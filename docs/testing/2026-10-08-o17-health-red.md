Date: 2026-10-08. Branch `task/mcsw-o17-health-red`, off main `de22959`.

## Cause per check

### 1. `delivery.recentErrorsHealthy` is false

`notifyAll` writes one notification row per active owner, all under the same `dedupe_key`. Each copy then has to deliver on its own:

- Operator 1 has a cell but no push subscription. Alerts that are not SMS-eligible have no channel for operator 1. Operator 1 is not counted as "unreachable" either, so the row retries five times and then dies with "No configured alert channel accepted this retry."
- Operator 82 has no cell and no push, so its copy dies too.
- Operator 35's SMS copy fails with 21610 every time.

So at least one copy of almost every alert fails, even when another owner received the alert. Every failed copy reached `recentErrors`, which therefore was never empty.

The health monitor's own alert, sent when health is red, fails the same way. That keeps `recentErrors` non-empty on its own: health could not go green because it had reported being red.

### 2. `shopBrain.durableFailures.healthy` is false (`notificationDead` 227)

`notification_delivery_dead` counted every unread, non-test dead row. That includes the per-owner copies above whose alert reached another owner. 140 + 10 + 30 of the 227 are the no-channel shape.

The 49 Twilio failures include 21610 rows. Before this change a 21610 failure was treated as transient: the alert was retried until `delivery_attempts >= 5`, and each attempt reached the same opted-out phone. The 21610 rows add to the count, and it never drains because nothing acknowledges old dead rows.

### 3. `inboundCallReceipts.providerVerified` is false

This field is hardcoded. `lib/call-health.ts` declares it as the literal type `providerVerified: false` and returns `false`. Nothing makes it true today. It does not feed `ok` or the health-monitor workflow's jq gate. It labels the receipt count as coming from the Shop Brain database, not from Twilio.

Making it true would take a new feature: reconcile receipts against Twilio's call log (the Calls API) and set the flag when they agree. No owner action changes it, and it is not why the endpoint returns 503.

## What changed

- **`lib/alert-failure-classifier.mjs`** (new, pure, with `.d.mts` types) classifies each dead or failed notification:
  - **Health-monitor alert** (`action_detail.source = 'health-monitor'`): diagnostic only. It never makes `ok` false.
  - **Covered by sibling**: a no-channel failure or a permanent Twilio recipient error, where another owner's copy with the same non-empty `dedupe_key` reached `accepted` or `delivered`. Not a durable failure.
  - **Everything else counts.** This includes total non-delivery (nobody got the alert) and real provider failures on a reachable channel, such as 30008, even when a sibling was delivered.
- **`lib/delivery-errors.ts`**: adds `listHealthDeliveryErrors()` and `listDeadNotificationRows()`. Both return `source`, `provider_error_code` (the Twilio code from the last `delivery_history` payload) and a `sibling_delivered` EXISTS. `listRecentDeliveryErrors()` and the Updates page are unchanged. The queries have no interpolations.
- **`app/api/health/route.ts`**:
  - `recentErrors` now holds only blocking errors.
  - `delivery.diagnosticErrors` holds the rest.
  - `notificationDead` is the classifier's `counted`.
  - `durableFailures` gains these diagnostics: `notificationDeadCoveredBySibling`, `optedOutOperatorIds`, `permanentSmsRecipients` (`{operatorId, twilioCode, reason}`) and `healthMonitorAlert` (`{count, lastAt, lastError}`). They carry operator ids, never phone numbers.
- **Permanent Twilio recipient errors**:
  - **The errors**:
    - 21610: opted out.
    - 21614: not a mobile number.
    - 21211, 21217, 21401, 21421: invalid number.
  - **`lib/notify.ts`**: a permanent error stops the inline retry at once. A first send, coalesced summary or scheduled retry that fails this way goes `dead` on that attempt instead of the fifth.
  - **`app/api/twilio/notification-status/route.ts`**: the status callback writes the same message.
  - **The message**: for 21610, `delivery_error` reads "The operator's cell opted out of texts (Twilio 21610). It gets no SMS until that phone texts START to the shop number. Not retried."
- **`scripts/ack-dead-notifications.mjs`** (new; not run): a one-shot owner script to clear the dead backlog.
  - It is a dry run by default.
  - `--apply` sets `read_at = now()` on unread dead notifications older than `--older-than-days` (default 14) that are not tests. A row counts as a test if any of these is set:
    - `is_test`;
    - the linked lead, person or event is marked as a test;
    - `action_detail.isTest`;
    - `[INTERNAL TEST]` in the title or body.
  - It prints counts only. It reads only `DATABASE_URL`.
  - Every interpolation is cast (`::int`).
- **Tests**:
  - `scripts/o17-health-red.test.mjs` (new, 11 tests) and `scripts/ack-dead-notifications.test.mjs` (new, 4 tests).
  - `scripts/inbound-call-alert-callbacks.test.mjs`: a new 21610 callback test, and the classifier added to the harness's import allowlist.
  - `scripts/s05-health-cache.test.mjs`: the removed `notification_delivery_dead` alias is dropped.

Schema: no change. Roles: unchanged. `is_test`: every new query excludes test rows, and the ack script never touches them.

## Questions for Fable

1. Should an owner with no channel for an alert class fall back to SMS when it has a cell, or be filed as "unreachable" up front so its copy is never written? This change stops those copies from turning health red. The routing that creates them is unchanged.
2. Should `accepted` (Twilio took the SMS, no delivery receipt yet) count as "sibling delivered"? This change says yes, because a later undelivered callback moves that sibling out of `accepted`.
3. The sibling `EXISTS` filters on `dedupe_key`, and no index leads with that column. With 10,000 rows per window this is probably fine. Should `(dedupe_key, delivery_status)` get an additive index?
4. A coalesced summary that dies does not get the "Alert delivery failed - " title prefix that first sends and scheduled retries get. This was pre-existing and is left as is. Fix it?
5. Should `/api/health` also report a raw total of non-test dead rows beside the classified `notificationDead`, so a classifier bug cannot hide a backlog?
